## What stays the same

- The app is still offline-first. SQLite on the device remains the source of truth for the screen; the server is a replica and a merge point, never a requirement for studying.
- Business logic stays in the app as pure functions (`src/logic`). The server does not run SM-2, scoring or readiness; it stores and merges study data, and each client derives schedules and stats from the merged history. That keeps the two repos free of shared code.
- The question bank stays bundled in the app. Serving bank updates from the server is an optional later phase.
- Sync is opt-in. A user who never signs in gets exactly v1.

Hard constraints:

- No `any`. Sync merge logic is pure functions with unit tests, separate from controllers and the ORM.
- The contract changes deliberately: additive changes within `/v1`, breaking changes only in a new version. The app's CI fails if its generated client no longer matches the spec version it pins.
- Every write the device sends is idempotent: replaying the same batch twice changes nothing.
- The server never trusts client clocks for ordering across devices beyond what the merge rules below allow. It stores answers as reported (including `isCorrect` and the question-bank version) and does not need the bank itself.
- Personal data is minimal: an account id, the provider subject, an optional email, and study data. Account deletion removes everything.
- Never write exam content. The question bank is mine.

## Data model and identifiers

Today's tables use integer autoincrement ids, which collide across devices. Migration 2 on the device adds:

- `uuid` (TEXT, generated on the device) on `answers` and `exam_attempts` — the global identity used by sync.
- `updated_at` (epoch ms) on every syncable row, and `deleted_at` for soft deletes (needed for "Reset progress" to propagate).
- A `sync_state` table: last server cursor received, last successful push time, device id.

Server tables hold the syncable data per user: `devices`, `answers`, `exam_attempts`, `settings`, plus `change_log` (monotonic `seq` per user) that drives pulls. There is no server-side review schedule: each device rebuilds `review_schedule` locally from the merged answers.

## Sync protocol

Push then pull, in one round trip where possible.

1. **Push:** the device sends rows changed since its last successful push (`updated_at > last_push`) with their uuids. The server upserts them with the merge rules below and appends to `change_log`.
2. **Pull:** the device sends its last cursor; the server returns every change with `seq > cursor` from other devices, plus a new cursor. The device applies them in one SQLite transaction.
3. **Triggers:** app start, return to foreground, after a practice session or exam submit, and pull-to-refresh on Progress. No background sync in the first version.
4. **Failure:** sync errors never block studying; they surface as a small "Last synced …" status in Settings with a retry.

Merge rules (pure functions in the API repo, each with unit tests; the app has matching tests for how it applies pulled changes):

| Data | Rule | Why |
| --- | --- | --- |
| Answers | Append-only set keyed by uuid; union of all devices | Answers are facts; nothing to resolve |
| Exam attempts | Keyed by uuid; `submitted` beats `in_progress`; two in-progress attempts on different devices both survive | An exam is taken on one device |
| Review schedule | Not synced. After applying a pull, the device replays SM-2 over the merged answer history for every question that changed | Avoids two devices fighting over intervals, and keeps SM-2 out of the server |
| Settings | Last writer wins per key by `updated_at`; the reminder time stays per device | Reminders are a device concern |
| Reset progress | Soft delete with a reset timestamp; anything older is dropped on every device | Otherwise the next sync restores it |

Open question for me: should a reset on one device wipe progress on all devices, or only that device? Recommend one.

## Build phases

Each phase ends with a check I run myself.

1. **API repo skeleton.** Create `cloudprep-api`: NestJS app with config, health check, structured logging, Docker Compose Postgres, migrations, OpenAPI generation, and CI that also publishes the spec as a build artifact.
   - Done when: `docker compose up` plus `npm run start:dev` serves `/v1/health` and `/docs` (Swagger UI), and CI is green.
2. **Contract in the app.** Add the client generator to this repo, pin the spec version, generate the client, and add a CI check that fails on drift.
   - Done when: the generated client type-checks against `/v1/health`, and changing the pinned spec without regenerating fails CI.
3. **Auth.** Sign in with Apple and Google on the device; the API verifies the identity token, creates the account and issues tokens; refresh rotation; sign-out; account deletion.
   - Done when: I can sign in on my A57 and on the iOS simulator as the same account, and deleting the account removes every row.
4. **Device migration 2.** Add uuids, `updated_at`, `deleted_at` and `sync_state` to SQLite with a tested migration that backfills existing rows.
   - Done when: migrating a copy of my real v1 database keeps every answer and exam, and the migration tests cover it.
5. **Sync protocol.** Push and pull endpoints with pure merge functions in the API, the matching spec update, and the device sync client with its triggers and local schedule rebuild.
   - Done when: unit tests cover every merge rule, including replaying a batch twice and two devices answering offline then syncing in either order, and the review queue is identical on both devices afterwards.
6. **Sync UX.** Sign-in screen, "Last synced" status, retry, and a first-sync choice when both the device and the account already have data.
   - Done when: answers made offline on the phone appear on the simulator after both come online, and a Maestro flow covers it.
7. **Deploy.** Container build, managed Postgres, secrets, and a production API URL configured per build profile.
   - Done when: the APK on my A57 syncs with the deployed API.
8. **Optional: bank updates.** The API serves a versioned question bank, validated on upload against a JSON Schema exported from the app's Zod question schema (so the rules live in one place); the app downloads it when online and falls back to the bundled one.
   - Done when: publishing a new bank version reaches the app without a new APK.

- Rate-limit auth and sync endpoints; never log tokens or study content.
